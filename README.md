## Сценарий владельца и гостя

В приложении один заранее заданный владелец календаря. Владелец и гость работают без регистрации и авторизации.

1. **Владелец создаёт тип встречи.** Указывает название, описание и длительность — например, «Знакомство», «Обсудим задачу», 30 минут.
2. **Гость открывает каталог типов встреч.** Смотрит описание и длительность, выбирает «Знакомство».
3. **Гость выбирает день.** Открывает календарь в пределах скользящего окна записи на 14 календарных дней и видит свободное время для выбранного типа встречи.
4. **Гость выбирает слот.** Например, 10:00–10:30. Длительность слота соответствует длительности типа встречи; весь интервал должен быть доступен владельцу.
5. **Гость подтверждает запись.** Заполняет имя и email и отправляет форму записи.
6. **Приложение создаёт запись.** Если интервал всё ещё свободен, гость видит подтверждение с типом встречи, датой и временем. Если время уже заняли, в том числе пока гость заполнял форму, пересекающаяся запись не создаётся.
7. **Владелец видит результат.** Открывает общий список предстоящих встреч всех типов и видит новую запись на «Знакомство» с выбранной датой и временем.

Время 10:00–10:30 приведено только для примера. Расписание — ежедневно 09:00–18:00, Europe/Moscow.

### Обязательные правила и границы

- Занятость общая для всех типов встреч: запись на 10:00–10:30 запрещает любую другую встречу, пересекающую этот интервал, даже частично. Встреча с началом ровно в 10:30 допустима, если остальное время свободно.
- Запрет пересечений действует и при одновременных запросах: из двух запросов на пересекающиеся интервалы успешно создаётся не более одной записи.
- Окно записи сдвигается с течением времени: сегодня и следующие 13 московских календарных дней; шаг доступных стартов — 30 минут.
- Регистрация, личные кабинеты, внешние календари и уведомления Cal.com в проект не входят.
- Данные хранятся в памяти процесса: перезапуск сервера сбрасывает каталог типов встреч и записи. Раздел владельца публичен: имена и email гостей доступны любому посетителю. Приложение предназначено только для учебного использования с тестовыми персональными данными.

### Требования к будущей реализации

- Приложение собирается в Docker-образ и запускается в контейнере.
- API описывается TypeSpec-контрактом; из него генерируется OpenAPI-спецификация, а из OpenAPI — клиентский SDK для фронтенда. До выбора инструментов необходимо проверить наличие генератора для языка фронтенда.
- Серверные типы и маршруты генерируются, если выбранный фреймворк это поддерживает. Иначе бекенд реализуется по контракту и проверяется тестами.

### Источники сценария

Сценарий учебного приложения основан на описании задания Хекслета. В [Cal.com](https://cal.com) просмотрен публичный гостевой путь до формы подтверждения; реальная бронь не отправлялась. Создание типа встречи и список владельца требуют входа, поэтому эти части изучены по официальной справке: [создание типа встречи](https://cal.com/help/event-types/create-first-event) и [просмотр записей](https://cal.com/help/bookings/manage-a-booking). Дополнительные возможности Cal.com не становятся требованиями нашего приложения.

## Стек

- Бекенд: Go, стандартный `net/http`, generated strict server от oapi-codegen.
- Фронтенд: TypeScript, React, Vite, React Router 7; страницы: главная, каталог типов встреч `/booking`, создание типа встречи `/admin`, страница ошибки.
- API: `api/main.tsp` → `api/generated/openapi.yaml` → Go API и TypeScript Fetch SDK (Hey API).
- Проверки: Go testing, golangci-lint, Oxlint, Oxfmt, tsc, Playwright; hk и commitlint для Git hooks.
- Окружение и задачи: mise; dev-процессы — mise daemons / pitchfork. Версии закреплены в конфигурации и manifests проекта.

Реализованы гостевая запись в `/booking`, создание типа встречи и список записей в `/admin`, а также контейнерный запуск. Вход не предусмотрен, внешняя публикация — отдельная задача.

## Запуск в контейнере

Нужен работающий Docker. Из корня репозитория:

```bash
docker build -t calendar-booking .
docker run --rm -p 127.0.0.1:8080:8080 calendar-booking
```

Для другого порта задайте его контейнеру и опубликуйте тот же внутренний порт:

```bash
docker run --rm -e PORT=18080 -p 127.0.0.1:18080:18080 calendar-booking
```

`PORT` имеет приоритет над `LISTEN_ADDR` и принимает только десятичные числа от 1 до 65535. Пустое или некорректное значение останавливает запуск. Без `PORT` сохраняется `LISTEN_ADDR`: в образе по умолчанию `0.0.0.0:8080`, при нативном запуске — `127.0.0.1:8080`.

Откройте http://127.0.0.1:8080/admin, создайте тип встречи и запишитесь на http://127.0.0.1:8080/booking. API доступен на том же адресе под `/api/`, например `/api/meeting-types`, `/api/booking-window`, `/api/availability` и `/api/health`; dev-серверы не нужны. Остановите контейнер через Ctrl+C. В образ включены данные часовых поясов Go, включая Europe/Moscow; системный часовой пояс не задаёт правила расписания.

Это учебный запуск, не настройка внешнего production-хостинга. Авторизации нет: раздел владельца и записи доступны всем. Используйте только вымышленные имена и email, никаких реальных персональных данных. Каталог типов встреч и записи изначально пусты и сбрасываются при перезапуске контейнера; постоянное хранение не настроено. После перезапуска проверяющий сначала создаёт тестовый тип встречи в `/admin`.

Контейнерная smoke-проверка собирает образ и проверяет внутренние порты 8080 и 18080 на отдельных контейнерах: API, прямые URL и сценарий в Chromium. Помимо Docker, нужны зависимости проекта и браузер Playwright (`mise run setup`, `mise run setup:e2e`):

```bash
mise exec -- node scripts/container-smoke.mjs
```

### MCP Render

Проектная конфигурация OpenCode читает ключ из локального файла `~/.config/opencode/secrets/render-api-key` вне репозитория. Сам ключ в конфигурацию не записывается. Создайте файл с доступом только для своей учётной записи и поместите в него только ключ, без передачи через чат или сохранения в истории команд. Проверяйте подключение в `/mcps`. Не помещайте ключ в Git или логи.

Classic key обладает широкими правами; предпочтителен scoped key при его доступности. После работы отзовите ключ в Render и удалите локальный файл: удаление файла само по себе ключ не отзывает. На бесплатном сервисе возможны сон и задержка пробуждения.

## Установка

Для локальной разработки нужны Git и **mise 2026.10.25**. Go, Node.js и остальные CLI устанавливает mise. Docker и WSL для этого не требуются; для контейнерного запуска нужен Docker.

Установите mise по [официальной инструкции](https://mise.jdx.dev/installing-mise.html). Для Windows есть проверяющий SHA-256 helper `scripts/install-mise.ps1`: он устанавливает mise в `~/.local/bin` без изменения постоянного PATH или профиля. Если политика PowerShell запрещает scripts, используйте ручную установку ZIP из официальной инструкции; менять ExecutionPolicy не нужно.

Если mise установлен в пользовательский каталог, на Windows достаточно добавить его в PATH **текущего** терминала:

```powershell
$env:PATH = "$HOME\.local\bin;$env:PATH"
mise --version
```

После клонирования:

```bash
git clone https://github.com/yurapriv/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install --locked
mise run setup
mise run setup:e2e
mise run setup:hooks
```

Перед `mise trust` прочитайте `mise.toml`, `hk.pkl` и `scripts/`: задачи исполняют локальный код. Установка hooks явная и действует только на этот клон. Локальный launcher сохраняет абсолютный путь к mise, поэтому Git/GUI не требуют изменения постоянного PATH. После переноса mise повторите `mise run setup:hooks`.

`setup` использует `npm ci` и Go modules; не устанавливает hooks и браузеры, не меняет глобальные настройки и не запускает серверы. `setup:e2e` отдельно устанавливает Chromium для Playwright; в CI на Linux он же ставит системные зависимости (`--with-deps`). Секретов и `.env` для каркаса не требуется.

## Использование

В двух терминалах:

```bash
mise run dev:backend
mise run dev:frontend
```

Откройте http://127.0.0.1:5173. Главная страница «Календаря встреч» ведёт в гостевой раздел `/booking` и «Админку» `/admin`; неизвестные адреса показывают страницу ошибки. Раздел `/booking` позволяет создать запись, `/admin` — создать тип встречи и просмотреть записи. Фронтенд обращается к Go API через прокси Vite `/api`, который удаляет этот префикс. Go API отвечает на http://127.0.0.1:8080; Vite также сохраняет прямые прокси `/meeting-types`, `/booking-window`, `/availability` и `/health`. Бекенд принимает `LISTEN_ADDR` (по умолчанию `127.0.0.1:8080`); `127.0.0.1:0` позволяет ОС выбрать свободный порт, если `PORT` не задан.

Фоновый запуск, состояние, логи и остановка:

```bash
mise daemons start backend frontend
mise daemons ls
mise daemons logs backend frontend
mise daemons stop backend frontend
```

Foreground- и daemon-серверы используют одинаковые порты: сначала остановите один вариант перед запуском другого. Автозапуск при входе в ОС/переходе в каталог не настраивается; daemons — экспериментальная возможность mise.

### Проверки и сборка

```bash
mise run check
```

Это же вызывает отдельный GitHub Actions workflow `quality` на каждый push: generation drift → форматирование → Go module integrity → lint → typecheck → сборка → тесты фильтра агента и Go → браузерные тесты Playwright → проверка конфигурации hooks и новых сообщений коммитов. Старые шаблонные коммиты до принятого правила не переписываются. При падении Playwright отчёты `playwright-report/` и `test-results/` сохраняются артефактом с коротким сроком хранения.

Отдельные команды: `mise run lint`, `mise run typecheck`, `mise run build`, `mise run test`, `mise run setup:e2e`. `test` сам собирает фронтенд и запускает Go- и Playwright-тесты: предварительный `mise run build` не нужен. `check` использует свою же сборку без повторной сборки фронта. Результаты сборки — `dist/server` (`server.exe` в Windows) и `dist/frontend/`. `npm run format` — отдельная изменяющая файлы команда; `check` ничего не исправляет и не добавляет в индекс.

Smoke-тест запускает настоящий Go-бинарник на назначенном ОС порту, проверяет HTTP-ответ по OpenAPI и завершает свой процесс. Браузерные сценарии этапа главной страницы и этапа каталога типов встреч (навигация, история, мобильная геометрия, клавиатура, создание типа) покрыты Playwright с одним движком Chromium; Vitest не подключён. Сгенерированный SDK используется страницами каталога и формы, проверка в браузере остаётся частью сценариев.

### Агент в GitHub

Workflow `.github/workflows/opencode.yml` предназначен для ответов и работы с кодом по комментариям владельца. Он использует GitHub App [OpenCode Agent](https://github.com/apps/opencode-agent) и закреплённую версию OpenCode V1 `1.19.5`; локальную версию OpenCode не меняет. Вместо готового composite action запускается та же команда `opencode github run`: это позволяет проверить SHA-256 архива и зафиксировать версию CLI независимо от кэша action. Результат появляется в комментарии issue или PR, а журнал — во вкладке [Actions](https://github.com/yurapriv/ai-for-developers-project-387/actions/workflows/opencode.yml).

- События — только `issue_comment` и `pull_request_review_comment` с типом `created`. Команды по умолчанию заданы явно: `/opencode` и `/oc`. Комментарии принимает только от владельца репозитория, ботов игнорирует. PR из форков отклоняются до передачи ключа модели; для комментариев к PR его исходный репозиторий проверяется через GitHub API.
- Модель — `opencode/glm-5.3-flash-free`. Она бесплатна ограниченное время; её доступность для V1 на раннере необходимо подтвердить первым запуском. Не переключайте workflow на платную модель без отдельного решения владельца.
- Публикация сессий отключена (`share: disabled`); в текущем V1 GitHub action вход `share` устарел и игнорируется. Контекст задачи всё равно отправляется провайдеру модели.
- В свежем окружении загружаются проектные `.agents/skills/` и `.opencode/skills/`, включая `to-spec`, `to-tickets` и `implement-spec`; перед вызовом агента workflow проверяет их наличие. Настройки трекера и команды проекта находятся в `docs/agents/` и `AGENTS.md`. V1 игнорирует поле `disable-model-invocation` в описаниях скиллов.
- Локальная конфигурация `.opencode/opencode.json` не загружается на раннере: она ссылается на отсутствующий там файл ключа Render. Поэтому MCP Render в этом workflow недоступен; локальная конфигурация остаётся без изменений. Корневой `AGENTS.md` передаётся V1 отдельно, поскольку автоматическое обнаружение инструкций при отключении проектной конфигурации тоже выключено.
- `contents: read` и `id-token: write` предназначены для checkout и обмена OIDC на токен приложения; checkout не сохраняет свои учётные данные. `pull-requests: read` нужен для проверки источника PR. `issues: write` и `GH_TOKEN` позволяют командам `gh` из проектных скиллов работать с issues; push и ответы встроенной интеграции выполняются через токен приложения.
- Время задания ограничено 30 минутами; на один issue или PR действует одна группа concurrency без отмены работающего задания. GitHub сохраняет не более одного ожидающего запуска в группе и может заменить его новым. Cancel workflow останавливает прогон, Disable workflow — будущие запуски; запрос к провайдеру уже может продолжаться.

Для подключения владелец устанавливает приложение на этот репозиторий и добавляет ключ OpenCode Console как Actions secret `OPENCODE_API_KEY` в Settings → Secrets and variables → Actions. Ключ нельзя помещать в репозиторий, комментарии или чат. Перед первым вызовом проверьте модель, права приложения и фильтры; после слияния workflow в `main` создайте issue и оставьте `/oc explain this issue`. Затем проверьте ответ и прогон в Actions. Для проверки настроек можно попросить агента назвать трекер из `docs/agents/`, доступные скиллы и команду `mise run check`.

#### Автоматический разбор новых обращений

Отдельный workflow `.github/workflows/triage.yml` запускается при `issues.opened`: владельцу не нужно писать `/oc`. Он принимает только issue, открытые владельцем-человеком; боты и другие авторы пропускаются. Перед установкой инструментов и ещё раз перед запуском агента фильтр запрашивает актуальное состояние issue через GitHub API: закрытые issue, PR и issue с меткой `ready-for-agent` пропускаются. Ошибка запроса останавливает запуск. Подготовленные через `to-spec` и `to-tickets` issue создаются в текущем GitHub workflow от бота и получают `ready-for-agent`, поэтому повторно не разбираются.

Метка может появиться после проверки: если подготовленное issue создаётся вручную от имени владельца и `ready-for-agent` назначается позже, агент может успеть начать разбор. Двойная проверка уменьшает это окно, но не устраняет гонку. События, созданные стандартным `GITHUB_TOKEN` другого workflow, обычно вообще не запускают новый workflow GitHub Actions.

Инструкция в workflow просит агента прочитать приложение и обращение, предложить категорию и состояние, задать вопросы и дождаться человека; разрешены комментарий с отметкой об ИИ и метки текущего issue. Инструкция запрещает реализацию, закрытие issue и создание спецификаций или тикетов. Это ограничение **в prompt, а не техническая изоляция**: GitHub-интеграция использует токен приложения, чьи права могут быть шире `GITHUB_TOKEN`. Проверяйте права установленного приложения и не считайте текст issue доверенными инструкциями. Не отправляйте через issue секреты: контекст передаётся провайдеру модели.

Workflow использует тот же секрет `OPENCODE_API_KEY`, модель и проверенную версию CLI, что и вызов по комментарию. `contents: read`, `issues: write` и `id-token: write` нужны для checkout, работы с issue и токена приложения соответственно; checkout не сохраняет учётные данные. Тайм-аут — 15 минут, concurrency — одна активная задача на issue без отмены работающей; ожидающий запуск в той же группе может быть заменён. Перед первым испытанием workflow должен быть в ветке по умолчанию: создайте тестовое обращение владельца, проверьте комментарий и журнал Actions, затем отдельно проверьте пропуск подготовленного issue. Если событие от бота подавлено самим GitHub, отсутствие запуска не доказывает работу фильтра: проверяйте его также тестами.

### Изменение контракта

Правьте `api/main.tsp`, затем запускайте:

```bash
mise run generate
mise run check
```

Generated OpenAPI, Go и SDK сохраняются в Git и вручную не редактируются. `generate` заменяет только принадлежащие генераторам каталоги `api/generated/`, `internal/api/`, `frontend/src/api/generated/`. Проверка актуальности генерирует во временное дерево и сравнивает весь состав файлов, включая новые и удалённые.

### Git hooks

- pre-commit: быстрые проверки staged-файлов, без исправлений и автоматического staging;
- commit-msg: Conventional Commits, например `feat: add meeting types`;
- pre-push: полный `mise run check`.

После нового клонирования установите hooks через `mise run setup:hooks`; CI работает независимо от их установки.

### Релизы

Workflow release-please пока запускается только вручную. Для автоматических запусков после настройки секрета и разрешений добавьте обратно запуск по push в `main`. Release-please собирает Conventional Commits в release PR с `CHANGELOG.md` и обновлением версии; после слияния PR создаются тег и GitHub Release. Публикация npm-пакета или контейнерного образа не настроена.

Версия `1.0.0` и журнал изменений перенесены из исходного проекта, но история Git, тег и GitHub Release в новом репозитории не создавались. Перед первым запуском определите базу выпусков нового репозитория и проверьте предложенную версию и журнал изменений: нельзя считать исходный тег существующим здесь.

`CHANGELOG.md` и `.release-please-manifest.json` формирует release-please; они исключены из проверки Oxfmt, поскольку генератор использует собственный формат. Содержание release PR по-прежнему проверяется при ревью; остальные файлы и проверки CI не исключаются.

Для работы workflow требуется Actions secret `RELEASE_PLEASE_TOKEN`: fine-grained PAT владельца или отдельного бота, ограниченный этим репозиторием, с правами Contents и Pull requests на чтение и запись. Отдельный токен нужен, чтобы PR и теги, созданные автоматизацией, запускали обычные GitHub Actions; стандартный `GITHUB_TOKEN` этого не обеспечивает. Токен не следует передавать в чат или хранить в репозитории. Владелец репозитория управляет сроком действия и ротацией токена. Если политика запрещает создание PR, разрешите это в настройках репозитория.

Перед слиянием release PR проверьте все обязательные CI-проверки и включите ссылку на связанную GitHub issue в итоговое сообщение коммита. Создание тега запускает также неизменяемый workflow Hexlet; для него нужен секрет `HEXLET_ID`.
