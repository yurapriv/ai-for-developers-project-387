# Создание коммита

## Границы задачи

- Запрос создать коммит или вызов `@commit` разрешает разобрать изменения, проверить их, подготовить индекс и создать коммиты в рамках запроса. Не запрашивай подтверждение плана, сообщений или отдельных коммитов.
- Если пользователь просит только план или сообщения, выдай их и не меняй индекс или рабочие файлы. Просьба изменить этот скилл не разрешает создание коммитов.
- Соблюдай `AGENTS.md` и вложенные инструкции для затронутых файлов. Оставляй рабочие файлы без изменений.
- Ограничься локальными коммитами: сохраняй существующий staging, настройки Git и авторство; не делай push, amend, rebase, reset, checkout файлов и не обходи hooks.

## 1. Изучи изменения

Выполняй команды отдельно, из корня репозитория:

```sh
git status --short --branch
git diff --stat
git diff
git diff --cached --stat
git diff --cached
git log -5 --format=%s
```

- Определи область по запросу и контексту задачи. Если область не ограничена, рассмотри все staged, unstaged и untracked-изменения. Если она ограничена, проверь весь индекс, чтобы не захватить в коммит изменения за её пределами.
- `git diff` не показывает untracked-файлы: получи полный список через `git ls-files --others --exclude-standard` и прочитай их перед включением в план. Ignored-файлы автоматически не включай.
- Разбей изменения по целям, а не по файлам: держи реализацию, её тесты и необходимую документацию вместе, а независимые исправления и рефакторинг — отдельно. Если цель одна, запланируй один коммит.
- Отнеси каждое изменение к группе или зафиксируй причину исключения. Не включай изменения, принадлежность которых к запрошенной области неясна. Если без них нельзя создать самостоятельный коммит, остановись и опиши блокер.
- Зафиксируй исходные границы индекса, особенно для частично staged-файлов. Если весь существующий staging относится к одной группе, начинай с неё, если позволяют зависимости. Если для выполнения пришлось бы снять существующий staging или захватить изменения вне группы, остановись до изменения индекса и опиши блокер.
- Если один файл содержит несколько логических изменений, выдели фрагменты diff для каждой группы. Объединяй группы только если они входят в область запроса и без друг друга не образуют самостоятельных коммитов.
- Проверь кандидатов на секреты, токены, приватные ключи, локальные env-файлы, дампы и ненужные артефакты. Секреты не включай в коммит и не цитируй в ответе; при обнаружении остановись и сообщи путь. `.gitignore` не защищает уже отслеживаемые файлы.
- При незавершённом merge/rebase или конфликтах остановись; разрешение конфликтов — отдельная задача. Если изменений нет, сообщи об этом, не создавая пустой коммит.

## 2. Составь план

- Определи порядок коммитов с учётом зависимостей. Для каждой группы зафиксируй цель, точные пути и фрагменты diff, сообщение и нужные проверки. Сообщение составляй по фактическому diff, а не по плану разработки.
- Если запрошено создание коммитов, сразу переходи к проверкам. Если запрошен только план или сообщения, верни запрошенное и перечисли существенные исключения.

### Формат сообщений

- Соблюдай явно заданные правила проекта. При их отсутствии используй Conventional Commits:

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footers]
```

- Типы: `feat` — новая возможность, `fix` — исправление; для остальных изменений выбирай подходящий `docs`, `test`, `refactor`, `perf`, `build`, `ci` или `chore`. Scope необязателен, не выдумывай его.
- По умолчанию пиши заголовок по-английски, в повелительном наклонении, без точки; стремись уложиться в 72 символа. Это рекомендация, не требование спецификации.
- Body добавляй, только если нужно объяснить причину или важное ограничение. Для несовместимых изменений используй `!` или footer `BREAKING CHANGE: ...` и опиши последствия. Не выдумывай номера задач, результаты тестов и trailers авторства.
- Если проект требует ссылку на задачу, возьми её из запроса или однозначного контекста работы. Если ссылку установить не удалось, сообщи об этом и не создавай коммит для этой группы.

## 3. Проверь изменения

- Сначала выбери объём проверок по фактическому diff и правилам `AGENTS.md`. Тип коммита `docs` или расширение `.md` сами по себе не означают, что изменения только документационные. Учитывай staged, unstaged и untracked-файлы; не объявляй смешанное рабочее дерево docs-only.
- **Только документация**: изменены лишь поясняющие тексты, словарь, ADR, планы, `AGENTS.md` или инструкции скиллов, без изменений кода, API-контрактов, скриптов, зависимостей и исполняемой конфигурации. Проверь содержание и применимое форматирование только изменённых документов, а также diff на ошибки пробелов. Проверки ссылок или метаданных запускай, если они предусмотрены проектом для этих документов. Если форматтер игнорирует файл, не выдавай это за проверку его форматирования.
- Для docs-only достаточно этих точечных проверок: не запускай вручную полный check/pipeline, генерацию, линтеры кода, typecheck, сборку или тесты, не устанавливай toolchain и зависимости ради коммита. Исключение — явный запрос пользователя или обязательное требование проекта. Существующие hooks и CI оставь работать как настроено; это правило не разрешает их отключать, обходить или запускать весь pipeline дополнительно вручную.
- **Код или смешанные изменения**: найди команды проверок в инструкциях, manifest/task-runner конфигурации и CI. Запусти относящиеся к запланированным группам проверки, включая полный check, когда он требуется проектом, соблюдая установленный порядок.
- Не придумывай команды и не устанавливай новый toolchain ради коммита. Если проверки отсутствуют или недоступны, явно укажи это; не выдавай отсутствие запуска за успех.
- Учитывай, что проверки рабочей директории видят и незакоммиченные изменения других групп. Не утверждай, что каждый промежуточный коммит проверен изолированно, если проверялось только общее состояние.
- При ошибке проверки останови последовательность и сообщи результат. Выбирай команды проверок, которые не меняют рабочие файлы.

## 4. Создай коммиты

Для каждой группы по порядку:

- Перед staging повторно проверь status и diff. Не включай новые или изменившиеся фрагменты без повторного разбора и нужных проверок; если их нельзя безопасно отделить, остановись и сообщи причину.
- Подготовь в индексе только её изменения. Добавляй целые файлы через `git add -- "путь"` лишь когда все их изменения относятся к группе. Для отдельных фрагментов используй проверенный patch и `git apply --cached`. Если разделение небезопасно, остановись и сообщи причину. Не используй `git add .`, `git add -A`, `git commit -a` или принудительное добавление ignored-файлов.
- Просмотри **полный** `git diff --cached` и `git diff --cached --stat`, затем выполни `git diff --cached --check`. Если проверка не прошла или состав индекса не совпадает с группой, остановись и сообщи причину. Если расходится только текст сообщения, исправь его по staged diff.
- Выполни `git commit -m "<заголовок>"`; при необходимости передай body и footers отдельными `-m`. Передавай текст безопасно для текущей оболочки, без интерполяции содержимого сообщения.
- При отказе hooks остановись и сообщи причину. После исправления повтори проверки и обзор индекса.
- После успешного коммита выполни:

```sh
git log -1 --format=fuller --stat
git status --short
```

- После каждого коммита проверь оставшиеся изменения перед переходом к следующей группе. При сбое останови последовательность, сохрани уже созданные коммиты и сообщи, какая часть плана осталась невыполненной; не откатывай историю автоматически.
- В итоговом ответе перечисли короткие hash и заголовки всех созданных коммитов, выполненные проверки и существенные пропуски. Для docs-only явно укажи, что полный цикл проверок кода не запускался, поскольку менялась только документация. Сообщи, какие изменения остались незакоммиченными. Не утверждай, что CI прошёл, без подтверждения.
